# ADR-0003: Use UUID as Primary Keys

**Status:** Accepted

## Context

Every persistent entity in CareerHub requires a unique identifier.

The identifier must remain stable throughout the entity's lifecycle, be exposed through the REST API, and support the long-term evolution of the application.

Several identifier strategies were considered, including sequential numeric identifiers (Long/BIGSERIAL) and UUIDs.

## Decision

CareerHub uses UUID as the primary key type for every persistent entity.

Identifiers are generated by the application before persistence rather than by the database.

Every entity uses a single primary key column named `id`.

This strategy is applied consistently across the entire domain model.

## Consequences

### Positive

- Prevents predictable sequential identifiers from being exposed through the API.
- Provides globally unique identifiers.
- Simplifies future integrations with external systems.
- Keeps identifier generation independent of the database.
- Provides a consistent strategy across all entities.

### Negative

- UUIDs consume more storage than numeric identifiers.
- Indexes are slightly larger.
- UUID values are less human-readable during debugging.

These drawbacks are considered acceptable given the expected scale of the application and the long-term benefits of a unified identifier strategy.

## Alternatives Considered

### Long (BIGSERIAL)

A sequential numeric identifier was considered because it is simple, efficient, and commonly used in relational databases.

Rejected because sequential identifiers expose information through the API and offer less flexibility for future distributed scenarios.

### ULID

ULID was considered due to its lexicographical ordering and improved readability compared to UUID.

Rejected because it introduces additional complexity without providing sufficient practical benefits for the current scope of the project.
