# Database Design

## 1. Design Goals

The database has been designed to provide a reliable, consistent, and maintainable persistence layer for CareerHub.

The primary objectives of the database design are:

- Preserve data integrity through well-defined relationships and constraints.
- Accurately represent the application's domain model.
- Minimize data duplication by following normalization principles where appropriate.
- Support future feature expansion without requiring major schema redesigns.
- Keep the schema easy to understand and maintain.
- Ensure that all schema changes are version-controlled and reproducible.

The database design prioritizes correctness and maintainability over premature optimization.

## 2. Database Technology

CareerHub uses PostgreSQL as its primary relational database management system.

PostgreSQL was selected because of its reliability, strong SQL compliance, excellent support for relational data modeling, and seamless integration with the Spring ecosystem.

Persistence is implemented using Spring Data JPA with Hibernate as the ORM provider.

Database schema changes are managed through Flyway migrations, ensuring that every structural modification is version-controlled, reproducible, and consistent across all environments.

## 3. Naming Conventions

To maintain consistency throughout the project, the following naming conventions are applied to the database schema.

### Tables

- Table names use singular nouns.
- Names are written in snake_case.

Examples:

- user
- company
- job_offer
- job_application
- interview
- task

### Columns

- Column names use snake_case.
- Foreign keys follow the `<entity>_id` convention.

Examples:

- company_id
- application_id
- created_at
- updated_at

### Primary Keys

Every table contains a single primary key named `id`.

### Foreign Keys

Foreign key constraints are explicitly defined and named consistently to improve readability and simplify database maintenance.

## 4. Primary Keys Strategy

CareerHub uses UUIDs as the primary key type for every entity in the system.

UUIDs provide globally unique identifiers without exposing predictable sequential values through the REST API.

Primary keys are generated by the application layer before persistence, ensuring database independence and allowing entities to be uniquely identified throughout their lifecycle.

Every table contains a single primary key column named `id`.

This strategy provides a consistent identification mechanism across the entire domain model while supporting future scalability and external integrations.

## 5. Entity Relationships

The database schema reflects the relationships defined in the domain model while enforcing referential integrity through foreign key constraints.

The following relationship types are used throughout the system:

| Relationship | Cardinality |
|--------------|-------------|
| User → Company | One-to-Many |
| User → Job Application | One-to-Many |
| Company → Job Offer | One-to-Many |
| Company → Job Application | One-to-Many |
| Job Offer → Job Application | One-to-Many (Optional) |
| Job Application → Interview | One-to-Many |
| Job Application → Task | One-to-Many (Optional) |
| User → Task | One-to-Many |

All relationships are implemented using explicit foreign key constraints.

Optional relationships are represented through nullable foreign keys when appropriate.

## 6. Constraints and Integrity Rules

The database is responsible for preserving structural integrity, while business rules remain the responsibility of the application layer.

The following principles apply throughout the schema.

### Primary Keys

Every table contains a UUID primary key named `id`.

### Foreign Keys

All relationships are enforced through explicit foreign key constraints.

### Required Fields

Mandatory attributes are defined using `NOT NULL` constraints whenever applicable.

### Uniqueness

Unique constraints are applied only when required by the domain model.

Examples include:

- User email addresses.
- User usernames.

### Referential Integrity

Foreign key constraints guarantee that every relationship references an existing record.

### Deletion Policy

The database follows a restrictive deletion strategy.

Entities cannot be deleted while dependent records still exist.

Deletion must always be handled explicitly by the application.

### Business Rules

Business-specific validations are intentionally implemented in the service layer rather than through complex database constraints.

This separation keeps the persistence layer focused on data integrity while allowing business rules to evolve independently.

## 7. Auditing Strategy

Every persistent entity includes auditing information to track its lifecycle.

The following audit fields are present in all tables:

- `created_at`
- `updated_at`

These fields are automatically managed by the application and should never be modified directly by clients.

Future versions may introduce additional auditing fields such as:

- `created_by`
- `updated_by`

This strategy improves traceability while keeping the initial implementation simple.

## 8. Indexing Strategy

Indexes are introduced to improve query performance while avoiding unnecessary overhead during write operations.

Primary keys and foreign keys are indexed by default.

Additional indexes are created only when justified by actual query patterns or performance requirements.

The database schema prioritizes correctness and maintainability before optimization.

Performance improvements should be driven by measurement rather than assumptions.

## 9. Schema Evolution

Database schema changes are managed through Flyway migrations.

Every structural modification to the database is introduced as an incremental migration, allowing the schema to evolve in a controlled and reproducible manner.

Existing migration files are never modified after being applied.

Instead, every change is introduced through a new migration.

This approach ensures consistency across development, testing, and production environments while preserving the complete history of the database schema.

## 10. Future Considerations

The database has been designed to support the long-term evolution of CareerHub.

Future versions may introduce additional entities and relationships without requiring fundamental changes to the existing schema.

Potential future extensions include:

- Document management
- Notifications
- Calendar events
- Skills management
- Artificial intelligence features
- External platform integrations

The relational model has been intentionally designed to remain stable as new capabilities are introduced.

Future database optimizations should prioritize maintainability and data integrity over unnecessary complexity.
